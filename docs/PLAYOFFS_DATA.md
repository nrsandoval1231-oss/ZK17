## Source-backed update workflow (2026-11-01 upgrade)

The current UIL page links the exact 2026 MaxPreps competition. The HTML is publicly retrievable without running JavaScript. Its 64-position bracket contains stable matchup UUIDs, school UUIDs, district seeds, feeder UUIDs and winner advancement edges. A November 1 live dry run recognized all 63 nodes and produced **zero observations**: placeholders remain unassigned. UIL lists November 7 district certification and November 12–14 first-round games; those date windows are not individual kickoff times.

1. `npm run playoffs:sync` is a read-only dry run. It fetches the UIL entrypoint, discovers the exact approved competition link, follows only the single inventoried MaxPreps canonical redirect, and validates the complete seed/feeder/advancement graph. A partial page, wrong season/division, changed seed ordering, unknown markup or ambiguous identity fails closed. No fuzzy matching or standings-based qualification inference occurs.
2. `npm run playoffs:sync -- --apply` runs the same checks and atomically updates `content/playoffs/verified.json` only if accepted facts change. It reuses `applyObservation` / `validateTournament` through the shared `artifact.ts` journal replay and batch transaction. One-sided confirmed qualifiers are allowed; alignment alone still assigns nobody. New school IDs come from stable MaxPreps UUIDs; their district/region comes from their explicit first-round seed placement in the UIL-linked bracket. Exact known aliases preserve Anna's existing identity. External bindings are retained as `maxpreps:<school UUID>` aliases. Ambiguous names or changed stable identities require review.
3. Final import requires `has-result`, two numeric scores and exactly one explicit `matchwinner`. The existing domain validator checks score range, non-tied scores, matching winner, distinct known opponents, district/region, every feeder and downstream propagation. Incomplete/live scores, forfeits without numeric scores and unfamiliar status markup require the existing manual update path. A later-round name alone cannot prove advancement; a final must justify every feeder. Normalization follows the evolving validated transaction, so source blanks never erase winners advanced earlier in the same poll.
4. Schedules come only from a game link inside its bracket matchup. The detail page must contain one Football `SportsEvent`, matching game URL, both exact 2026 team schedule URLs and a complete 2026 `startDate` with explicit timezone within the playoff season. Bracket order is preserved even when the detail page lists home/away in reverse. Missing/failed details leave qualifiers usable and kickoff pending; they appear as warnings. Canceled/postponed structured events require review. School addresses and round date ranges never become venues or kickoff times. Venues remain manual until a verified venue-specific source is supported.
5. Every changed observation references an immutable content-derived source ID, HTTPS URL, retrieval/verification time and public `source-adapter:maxpreps-v1` audit label. MaxPreps is honestly classified as `secondary`, with its UIL linkage explicit. It cannot overwrite an existing official-school/UIL observation. Each generated source also retains immutable optional `evidence` URL/SHA-256 entries for the UIL entrypoint, bracket and (when used) game detail. A detail-backed source ID hashes both bracket and detail content, so participant/result provenance cannot drift. The run report additionally retains retrieval metadata, accepted observations and warnings. Fetching or re-fetching alone does not advance the displayed verification timestamp.
6. Identical facts at **any** game status are no-ops, even if page ads or retrieval timestamps change. Conflicting participants, finals, occupied advancement slots, stale/future evidence or invalid downstream state abort the entire batch and leave the original JSON byte-for-byte unchanged. Raw HTML and an error report remain available for review. A source temporarily dropping a participant does not erase prior verified facts. Existing final facts are immutable. A newly supplied kickoff for a final is retained only as a warning for manual review; it does not overwrite the final or stall unrelated updates. Genuine corrections require a dedicated reviewed journal correction and complete replay.
7. The existing Actions workflow now polls every six hours in November/December, with a runtime gate limiting actual sync work to November 1–December 20, **2026**. Manual dispatch is available. One `automation/playoff-data-2026` branch and data-only PR are maintained, instead of committing directly to main. Each run replays pending branch observations before accepting more evidence. No changed facts means no commit/PR. Conflicts or unexpected branch files stop publication. Merge the data PR to use the existing deployment configuration. **The implementation PR must first be merged for this workflow to become active.**
8. GitHub must permit Actions to create pull requests. A token-created PR may not trigger other Actions; run any required checks manually before merging. Protected branches remain respected. If PR creation is disabled, the job fails visibly after pushing the validated data branch: open a PR from that branch. No PAT, paid service, database or additional deployment service is required. The HTML evidence artifact is retained 14 days; source hashes/URLs and accepted observations are retained in each data commit under `content/playoffs/evidence/latest-sync.json` and the journal.

### Cost and external scheduling

The sync command is runner-independent: an existing machine/cron can run it from a clean checkout, review its diff and push a data PR using the same path. To avoid GitHub Actions minutes entirely, remove the workflow's `schedule` stanza and run `npm ci --ignore-scripts` followed by `npm run playoffs:sync -- --apply` on that runner. Do not run two writers in the same checkout. The importer refuses a changed input artifact before atomic replace; isolated checkouts plus non-force git pushes are the concurrency boundary. Raw sync HTML/reports are ignored under `artifacts/playoffs/sync/`; do not serve them as site assets.

The season gate prevents source retrieval outside 2026, but cron cannot express a year: remove its schedule stanza after the season to eliminate future gate-only runner starts. No external scheduler was provisioned or credentials changed by this upgrade.

### Manual updates and correction fallback

`npm run playoffs:retrieve` still retrieves the four existing official documents for review, using the shared bounded HTTP helper. `npm run playoffs:update -- apply /path/to/reviewed-observation.json` and `npm run playoffs:validate` remain supported. A manual observation uses the existing `Observation` schema with stable IDs, known source, timezone-bearing `verifiedAt` and public reviewer label. Optional home/away names resolve through exact aliases. Prebuild and the site continue reconstructing the same journal/graph. For verified corrections, retain conflicting evidence, edit the affected journal entry in a dedicated PR and replay the full graph, including any dependent results. Never force the generated next-game state.

### Controlled validation

`tests/fixtures/playoffs/2026-placeholder.html` is a trimmed factual bracket subtree captured from the UIL-linked page on November 1. It contains no invented qualifier or result. Tests populate isolated copies with clearly named fixture teams and cover partial qualifiers, schedules/timezones/participant order, duplicate polls, changed identities, explicit winners, conflicting finals, damaged graphs, redirect allowlisting and a complete 64-team/63-final championship replay. CLI tests use temporary artifacts to prove dry-run, apply, repeat and rollback. Offline reproduction uses `--snapshot-dir DIR --artifact FILE --output-dir DIR`; the directory contains `uil.html`, `bracket.html`, and `snapshot.json` (`url`, `retrievedAt`, optional `details` map of game URL → HTML). Production scheduled runs never accept fixture input.

Final scores require two known distinct participants, nonnegative integer scores, a non-tied complete score and an **explicit** winner matching that score. Live/incomplete/tied scores never advance. Scheduled games require kickoff; postponed/canceled games carry no scores/winner. Source/review times cannot be future or stale. Football scores above 200 require special manual model review and are rejected by the initial validator. District/region conflicts, duplicate first-round placements, malformed graph relationships, missing propagated winners and occupied downstream slots fail closed.

Conflicting finals are rejected, including a secondary source trying to replace an official result. Identical repeated finals are no-ops. For a genuine official correction, retain the conflicting snapshots, review and correct the affected journal record in a dedicated PR, then replay/validate the complete downstream graph. Do not force-overwrite the generated next-game state; existing dependent results may require explicit correction too. Git preserves the correction audit trail.

Keep private notes and credentials outside public artifacts. Reviewer labels should be safe public audit labels. Test fixtures remain under tests or isolated `/tmp` builds; never put fixture opponents/scores in `content/playoffs/verified.json`.
