## 2. Native WebKit keyboard readiness invariant

The prior fix preserved an anchor only while `activeElement` remained the video. That was insufficient: WebKit’s native shadow-control Tab movement can scroll backwards before the alignment frame runs. The Film Room controls owner could then disable/remove the focused native control, causing a transient BODY focus state; a subsequent active-element check could no longer recover it. The frozen-HEAD full run’s real failure remains recorded in `/tmp/directors-final-browser.log` and its trace; the strong regression was not changed or skipped.

The repair uses an explicit native-keyboard frame token, acquired only by a keyboard control key while the native player is already ready/focused. Film Room’s existing controls owner honors that token so the control cannot disappear during the brief alignment interval. The hook queues alignment independently of pending hash state and tolerates transient BODY shadow-focus states. Tab, Space and native seek/volume arrows preserve readiness. It does not enable the opening aperture’s player before readiness.

Real external HTMLElement focus clears the hold through a document-level focus listener, covering header/skip controls outside the story as well as downstream story controls. That listener does not scroll. Existing Tab-only story recentering remains scoped to actual Tab focus. Pointer/touch, wheel, page-scroll keys, new anchor navigation and cleanup release the token. Thus external programmatic `preventScroll` focus is preserved, and intentional manual reverse scrolling can disable/hide the native controls again as before.

The original full native-player Tab traversal regression is unchanged. A new focused test covers ArrowRight, Space and ArrowUp readiness, external skip-link `preventScroll` focus without scroll movement, reacquiring readiness without pending hash alignment, then actual wheel/manual-touch emulation releasing the hold and reversing readiness. Pointer/programmatic story-focus regressions remain green.
